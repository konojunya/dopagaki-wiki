# レイアウトの選び方

エージェントが調査後、各スライドの主張と原稿を組み立てる時点で `content.layout` を指定する。CLIは指定されたレイアウトを検証・描画する。キーワードからの自動分類や、実行時のLLMによる選択は行わない。

## 判断する順序

1. この1枚を見て何を理解してほしいか、`claim` を一文にする。
2. 下表で、その主張に必要な関係を選ぶ。「見た目を変えたい」だけの理由では選ばない。
3. その型の項目数に収めて原稿と対応させる。図中の名称を読み上げでも使う。
4. `validate` → `preview` で参照・収まりを調べ、実際の画像で関係が伝わるか確認する。長すぎる場合は文字を縮めず、主張を分割する。

| 理解してほしい関係       | layout         | 選択の基準・例                                          |
| ------------------------ | -------------- | ------------------------------------------------------- |
| 教材の題名と今回の話題   | `title`        | 1枚目専用。短い話題を1〜3点、タイトルコールを添える     |
| 結論とその理由           | `key`          | 最初の答え、最後の要約。理由は3点まで                   |
| 複数の対象の違い         | `compare`      | 同じ軸で型・機能・選択肢を比較する                      |
| 同じ対象の変化           | `before-after` | 修正前後、導入前後。左右は同じ粒度・観点にする          |
| 順に進む処理             | `flow`         | 2〜3段階の手順。主体間の往復は `sequence`               |
| 主体間のやり取り         | `sequence`     | 誰から誰へ何を渡すか。上から時間順、2〜3主体・3通信まで |
| 条件による二択           | `branch`       | 条件を疑問文にし、「はい」「いいえ」の結果を明示        |
| 全体に対する部分         | `focus`        | 2〜3部分を並べ、選択部分を右で説明。接続関係は表さない  |
| コードとその意味         | `code`         | 短いコードと最大3つの説明。言語を明示する               |
| 数・ビットの構造         | `example`      | セルと式に具体的な値を載せる                            |
| 上記に収まらない図や画像 | `visual`       | 確認済みSVG、画像、公式ロゴなど。出所を記録する         |

複数に当てはまる場合は、主張の中心にある関係を優先する。たとえば「キャッシュがあると処理が変わる」は、条件を教えるなら `branch`、生成時間の改善を比べるなら `before-after`。前提も説明したい場合は別スライドにする。テンプレートの選択基準と入力制約で判断を揃えるが、内容が正しいかの確認はエージェントが行う。

## 段階表示

`flow.activeStep` と `sequence.activeMessage` は **1始まり**。省略すると全体表示、指定するとその項目だけ青い淡色背景と記号または太線で強調する。他の項目を隠したり、薄くして読みにくくしたりしない。

段階表示は、同じ図を持つ複数スライドを順に見せる。図の項目・順序・タイトルを揃え、強調番号と `narration` を変更する。slide / narration ID はそれぞれ一意にし、各段階も objective に対応させる。読み上げが終わると次のスライドに切り替わる。1枚の途中で強調が動くアニメーションではない。

同じ図だからという理由だけで音声を繰り返さない。各スライドでは強調中の項目だけを説明し、必要なら最後に全体をまとめる。`examples/layouts.story.json` に新しい4型と、3段階の表示例がある。
